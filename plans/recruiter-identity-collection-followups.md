# recruiter-identity-collection-followups

Status: ready-to-implement
Owner: codex
Last updated: 2026-04-27

## Problem
The initial identity-collection implementation landed, but the review found five lingering defects that still threaten live runs: resume metadata becomes self-contradictory after the first attach, cross-query selection can try to open/save a card from the wrong search page, `fit_gated_save` still calls `full_judge` before post-open identity confirmation, `identity_collect` leaves canonical identity/collection fields blank on several non-open terminal paths, and the new direct LinkedIn hint anchor path is effectively inert on real GitHub-sourced public LinkedIn URLs.

## Goal
Stabilize the new identity-collection workflow so resume semantics, multi-query provenance, post-open evaluation ordering, row semantics, and direct-hint anchoring all match the intended contract before the next staged live run.

## Non-goals

- Do not redesign the broader identity scorer or ambiguity thresholds in this slice.
- Do not change the saved/collected export contract again unless required by one of the defects below.
- Do not refactor the browser layer beyond the minimal query-replay/open-save fix needed here.

## Assumptions

- `plans/recruiter-identity-collection-first.md` remains the canonical implementation plan for the shipped v1 slice; this file is only the follow-up stabilization pass.
- The current on-disk artifacts under `output/runs/...` are still projection-only and can be regenerated by rerunning the tool.
- It is acceptable to require fresh output directories for already-corrupted partial runs, but new runs must resume cleanly once this slice lands.

## Seam

- `tools/run_recruiter_identity_resolver.py` owns the resume metadata bug and the synthesized failure-row semantics.
- `linkedin/recruiter_identity_resolver.py` owns query replay, direct-hint anchoring, post-open ordering, and terminal row field population.
- Tests should stay concentrated in `tests/test_run_recruiter_identity_resolver.py` and `tests/test_recruiter_identity_resolver.py`, with report coverage only if row semantics change materially.

## Proposed change

### 1. Fix resume metadata so first write and later resume compare the same shape

Current bug:

- `_seed_or_validate_run_metadata(...)` validates a dict that does not yet contain `recruiter_url_after_attach`.
- After attach, the runner mutates the on-disk metadata to add that key.
- On resume, the fresh in-memory dict still lacks the key, so validation fails immediately.

Required fix:

- Build the complete metadata dict only after browser attach / search preparation, when the actual Recruiter URL is available.
- Perform metadata validation once, against the final metadata shape, before processing the first unresolved lead.
- Stop mutating the metadata schema after validation.
- Keep `code_version`, `workflow_mode`, `project_url`, `max_cards`, `skip_profile_open`, `linkedin_brief_path`, and `recruiter_url_after_attach` all in the same initial write.

Implementation preference:

- Do not weaken metadata validation.
- Do not special-case missing keys on resume.
- Make the metadata write path single-shot and deterministic.

### 2. Replay the winning query before any profile open/save that depends on result-list DOM

Current bug:

- `_multi_query_lookup(...)` returns the winning profile and `resolved_query`, but the browser remains on the last query that happened to run.
- Later profile-open/save paths use rank-based focus plus `open_profile_by_url(...)` against the current page, which may not contain the selected candidate at all.

Required fix:

- Before any operation that opens or reopens a selected candidate from the results list, ensure the browser is on the query that surfaced that candidate.
- Introduce a small helper on the resolver, e.g. `_replay_query_for_candidate(...)`, that:
  - re-enters `resolution.resolved_query` or the passed query string,
  - waits for results,
  - then focuses/opens the candidate from the correct query surface.
- Use that helper in:
  - `_read_one_plausible_profile_review(...)` callers when the selected candidate came from multi-query lookup
  - `_attempt_identity_collect_save(...)`
  - `_reopen_and_save_if_save(...)`
- Do not rely on renumbered synthetic ranks alone for cross-query reopen behavior.

Acceptance rule:

- A candidate found only on query 2 or query 3 must still open and save correctly even if the final lookup loop ended on a different query.

### 3. Stop calling `full_judge` before post-open identity is confirmed

Current bug:

- In `fit_gated_save`, `_read_one_plausible_profile_review(...)` still calls `full_judge(...)` before `compute_post_open_identity_status(...)`.
- The later branch avoids applying the gate result when identity is unconfirmed, but the evaluative work already happened.

Required fix:

- Split profile-open reading into two phases:
  1. read profile status + innertext + extracted summary
  2. compute post-open identity status
- Only when `workflow_mode == "fit_gated_save"` and post-open identity is `confirmed` may the resolver call `full_judge(...)`.
- For unconfirmed identities in `fit_gated_save`, leave holistic fields empty and route directly to the synthetic identity-only terminal outcome.

Implementation preference:

- Keep `compute_post_open_identity_status(...)` pure.
- Prefer extracting a helper that returns `(profile_summary, profile_status, identity_status, identity_subreason)` before any fit call.

### 4. Populate canonical identity/collection fields on every terminal path in `identity_collect`

Current bug:

- `no_results`, `manual_review`, and `no_confident_match` paths still only populate legacy `final_action` fields.
- This leaves `identity_status`, `collection_action`, and `project_save_state` blank for many `identity_collect` rows.

Required fix:

- In `identity_collect`, every terminal row must set:
  - `identity_status`
  - `identity_subreason`
  - `collection_action`
  - `collection_subreason`
  - `project_save_state`
- Minimum mapping:
  - no results surfaced → `identity_status=no_match`, `collection_action=REJECT`, `project_save_state=not_attempted`
  - surface-level ambiguity / plausible-but-unconfirmed → `identity_status=ambiguous`, `collection_action=MANUAL_REVIEW`, `project_save_state=not_attempted`
  - tool failure → `identity_status=tool_failure`, `collection_action=MANUAL_REVIEW`, `project_save_state=not_attempted`
- Legacy `final_action` / `final_subreason` may still be filled for compatibility, but the new canonical fields must never be blank in `identity_collect`.

### 5. Make direct LinkedIn hint anchoring work with public LinkedIn URLs

Current bug:

- GitHub ingestion sets `linkedin_url_hint` from contact data, which is usually a public `/in/...` URL.
- `_apply_direct_hint_anchor(...)` only anchors when the hint exactly equals the Recruiter card’s `/talent/profile/...` URL.

Required fix:

- Support public LinkedIn hint anchoring in the Recruiter-first resolver.
- Accept one of these implementation approaches:
  - Preferred: if a public LinkedIn hint exists, compare it to extracted/public profile identifiers from the opened profile summary when available, and only then add the anchor.
  - Acceptable fallback: treat a public LinkedIn hint as a post-open identity-only anchor when the opened profile’s normalized public LinkedIn URL (if present in extracted data) matches it.
- Do not mark a Recruiter card as directly anchored purely because a public hint exists; the anchor still needs a concrete match.

If no reliable public-URL comparison is possible with current extracted data:

- explicitly disable the surface-time direct-hint anchor for public `/in/...` URLs,
- keep the evidence path only for true Recruiter `/talent/profile/...` hints,
- and add a note/TODO in code that public-hint anchoring requires extracted public profile identifiers.

This slice must choose one path decisively; do not leave the current inert exact-string behavior in place.

## Risks

- Replaying the winning query before open/save adds browser churn; keep it narrowly scoped to only the paths that need result-list DOM.
- Deferring `full_judge` until after identity confirmation changes call ordering in `fit_gated_save`; test both confirmed and unconfirmed opened-profile cases so this does not regress legacy behavior.
- Canonical field backfills in `identity_collect` will change summary counts; tests must assert the new values explicitly.

## Test strategy

- Narrowest relevant band first:
  - `pytest tests/test_run_recruiter_identity_resolver.py tests/test_recruiter_identity_resolver.py -q`
- Tests to add or strengthen:
  - resume succeeds when metadata already contains `recruiter_url_after_attach`
  - selected candidate from an earlier query is reopened/saved after query replay, not from the final query page
  - `fit_gated_save` unconfirmed opened profile does not call `full_judge`
  - `identity_collect` `no_results` / ambiguous / tool-failure rows all populate canonical fields
  - direct public LinkedIn hint either anchors correctly through the chosen comparison path or is explicitly ignored with tested behavior
- Full-suite gate before declaring done:
  - `make validate`
