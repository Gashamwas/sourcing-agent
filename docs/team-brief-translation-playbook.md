# Intake-To-Brief Workflow

Internal only: use this to understand and explain the overall workflow.

If you are answering the intake, use `docs/agent-brief-intake-template.md` instead.

This memo explains how the async intake connects to the brief and, from there, to the sourcing agent. It is meant to help you run the workflow cleanly and explain it simply if a peer asks how it works.

## 1. The Operating Model

The workflow has three parts:

- the hiring stakeholder explains the role in practical terms
- the brief owner translates that input into a structured brief
- the agent executes the brief and learns from pilot results

Each part has a different job.

The hiring stakeholder should not be asked to write the brief.

The brief owner should not invent hiring judgment from scratch.

The agent should not be expected to infer everything from the JD alone.

## 2. Why The Intake Asks For Judgment, Not Search Strategy

The intake is meant to collect the parts of the search that humans know best:

- what the role actually is
- what good looks like
- what often looks right but is usually wrong
- which examples feel clearly right, clearly wrong, or genuinely borderline
- where the search stands today

It is not meant to ask the stakeholder to precompute:

- keywords
- noisy terms
- search filters
- market traps
- agent logic

Those are better translated by the brief owner or learned by the agent during pilot runs.

## 3. What Goes In The Intake

The intake should collect six things:

- role basics
- what good looks like
- common lookalikes that are usually wrong
- examples, if available
- where the search stands
- anything else the brief owner should know

That is enough to draft a strong first brief.

## 4. How The Answers Get Used

Each part of the intake feeds a different part of the brief.

### Role Basics

Used for:

- title
- level
- geography
- source documents

### What Good Looks Like

Used for:

- the role summary
- capability areas
- the real yes / no boundary

### Common Lookalikes That Are Usually Wrong

Used for:

- non-fit patterns
- sharper boundaries inside capability areas

### Examples

Used for:

- calibrating ambiguous cases
- checking whether the brief would treat real people the right way
- improving the minimum bar and depth boundary

### Where The Search Stands

Used for:

- opening guidance
- search priorities
- additional search terms when needed

## 5. Keep These Concepts Separate

These concepts sound similar, but they do different jobs:

### What Good Looks Like

This defines what a real fit is.

### Common Lookalikes That Are Usually Wrong

This defines the tempting backgrounds that appear close but are usually not right.

### Examples

These anchor judgment with concrete people or concrete descriptions.

### Where The Search Stands

This explains how much prior search history should shape the opening strategy.

If these collapse together, the brief gets fuzzy fast.

## 6. What The Brief Owner Translates

Once the intake is back, the brief owner turns it into:

- a role summary
- capability areas
- a real yes / no boundary
- non-fit patterns
- LinkedIn snippet rules
- search guidance where needed

This is translation work, not copy-paste work.

The brief owner decides how to express the stakeholder's input in a way the agent can use consistently.

## 7. What The Agent Learns Later

The agent should learn certain things from execution, not from the intake.

That includes:

- which searches are noisy
- which populations are already exhausted
- which terms collide in practice
- which adjacent pools actually produce useful candidates

Those are pilot-stage learnings. Do not ask the stakeholder to predict all of them upfront.

## 8. How To Explain This To A Peer

If someone asks how the intake connects to the agent, the shortest honest answer is:

> The intake gives the agent better judgment, not just more keywords. It tells the system what strong looks like, what often looks similar but is usually wrong, and what context the JD misses. I turn that into a structured brief, and the agent uses that brief to decide who to surface and who to skip.

That explanation is usually enough.

## 9. How To Socialize The Workflow Later

Do not over-socialize the workflow before it has worked once.

The clean sequence is:

1. Get one async intake back.
2. Draft one brief.
3. Run one limited pilot.
4. Review the outputs.
5. Tighten the brief.
6. Only then explain the broader workflow to more people.

That keeps the process grounded in results instead of theory.

## 10. Sanity Check

The workflow is in good shape when all three of these are true:

- the stakeholder can answer the intake without needing extra reading
- the brief owner can draft a usable brief from those answers
- the agent can run on that brief and produce outputs that feel directionally right

If any one of those breaks, fix the workflow there instead of adding more process around it.
